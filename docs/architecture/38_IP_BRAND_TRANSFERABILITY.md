# IP, Brand and Transferability

## Goal

Build an asset that can later be transferred/sold without untangling the Owner's personal environment.

## Inventory

Maintain:
- source code ownership/license;
- character assets;
- visual style assets;
- music/fonts;
- provider-generated assets;
- channel branding;
- domain/site;
- documentation;
- prompts/templates;
- datasets/evidence snapshots where rights permit.

## Third-party brands

Internal model/provider identity may use real technical names.

Public characters should support fictional aliases.

Do not assume:
- provider logos;
- trademarks;
- model names;
are available for merchandise/character branding.

## Account separation

Prefer business-controlled:
- YouTube channel/Brand Account setup where suitable;
- domain;
- email;
- cloud;
- provider accounts.

Document accounts that cannot be transferred and the replacement process.

## Export package

Future sale export should include:
- DB/export excluding secrets;
- assets;
- character bibles;
- prompts;
- policies;
- operational docs;
- release info;
- channel/account inventory;
- license inventory;
- backup;
- setup checklist.

## Secrets

Buyer/new Owner reconfigures credentials.

Never package personal tokens in export.

## Provenance

Published content should be traceable enough to answer:
"Who/what created this and under what usage basis?"


## V4 character-brand strategy

For long-term sale/merch transferability, prefer studio-owned public character IP.

Support mapping:
`TechnicalAgentIdentity`
→ `PublicCharacterAlias`.

Example:
internal model/provider may change while public character brand remains studio-owned, if Owner chooses that strategy.

If public character directly uses another company's model/trademark name, flag transferability/merchandising risk.

Marketing, Legal and IP systems should coordinate before commercialization.
